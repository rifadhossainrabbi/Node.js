# Raw Node.js + TypeScript — Project Setup & Code Notes

This repository is a small **Raw Node.js** learning project. It uses Node.js's built-in HTTP module directly, without Express or another backend framework. TypeScript is used for writing typed JavaScript, and `tsx` is used to run TypeScript files during development.

> Goal: understand what each file, configuration, dependency, and command does—and why it is used—rather than memorizing commands.

---

## 1. Project Structure

```text
node/
├── node_modules/       # Installed packages (generated by npm; don't edit manually)
├── src/
│   └── server.ts     # Main HTTP server code
├── package.json       # Project metadata, scripts, and dependency lists
├── package-lock.json  # Exact dependency versions npm installed/resolved
├── tsconfig.json     # TypeScript compiler configuration
└── README.md         # These notes
```

### Why this structure?

- **`src/`** keeps our source code separate from configuration and generated files.
- **`server.ts`** is the entry point for the server we are currently learning to build.
- **`node_modules/`** contains packages installed by npm. It is not normally committed to Git.
- **`package.json`** describes the project and provides shortcuts (scripts) for commands.
- **`package-lock.json`** records the dependency tree so installs can be reproduced more consistently.
- **`tsconfig.json`** tells TypeScript how to understand and check our `.ts` files.

## 2. Setup Commands — What They Do and Why

Run commands from the project root (the folder containing `package.json`).

### `npm init -y`

Creates a `package.json` with default values. The `-y` flag accepts the default answers automatically. **This project already has a `package.json`, so you don't need to run this again.**

### `npm i -D typescript`

Installs TypeScript as a **development dependency**.

- `npm` — Node Package Manager.
- `i` / `install` — install the requested package.
- `-D` / `--save-dev` — add it under `devDependencies`, because the TypeScript compiler is primarily a development/build tool and isn't required as a runtime dependency for compiled JavaScript.
- `typescript` — the TypeScript compiler and its tooling (`tsc`).

### `npm i -D @types/node`

Installs TypeScript declaration files for Node.js APIs. These types help TypeScript understand Node-specific objects and functions (for example, `http`, `process`, and `Buffer`) and provide editor autocomplete/type checking. They do not add Node.js itself to the project.

### `npm i tsx`

Installs `tsx`, a tool that can execute TypeScript files directly during development. It avoids manually compiling the `.ts` file first for each run. This project lists `tsx` in `dependencies`; it can also commonly be placed in `devDependencies` for a development-only setup.

### `npm run dev`

Runs the `dev` script defined in `package.json`. In this project, the script is:

```bash
tsx watch ./src/server.ts
```

- `tsx` — executes the TypeScript entry file.
- `watch` — watches for changes and restarts/re-runs the process when files change.
- `./src/server.ts` — the file to run.

Use this while learning and developing. Stop the process with **Ctrl + C** in the terminal.

### `npx tsc --noEmit`

Runs TypeScript's type checker against the project configuration, but `--noEmit` tells it not to write compiled JavaScript or other output files. Useful for checking types without generating build files.

### `npx tsc`

Runs the TypeScript compiler using `tsconfig.json`. Depending on the configuration, it type-checks and emits compiled files. In this project's config, `rootDir` is `src` and `outDir` is `dist`, so emitted files are placed in `dist/`.

## 3. `package.json` Explained

Current project configuration (important parts):

```json
{
  "name": "node",
  "version": "1.0.0",
  "main": "server.ts",
  "scripts": {
    "dev": "tsx watch ./src/server.ts",
    "test": "echo \"Error: no test specified\" && exit 1"
  },
  "type": "module",
  "devDependencies": {
    "@types/node": "...",
    "typescript": "..."
  },
  "dependencies": {
    "tsx": "..."
  }
}
```

### Properties

- **`name`** — package/project name.
- **`version`** — current package version.
- **`description`** — short project description (currently empty; you can fill it in later).
- **`main`** — package entry point metadata. It currently says `server.ts`; for a compiled production entry, this would normally be updated to the emitted JavaScript path (for example `dist/server.js`) when you set up a production build. This field does not control the `npm run dev` script.
- **`scripts`** — named command shortcuts. `npm run dev` runs the `dev` entry.
- **`test`** — currently a placeholder that prints an error and exits; no test suite is configured yet.
- **`type: "module"`** — tells Node to treat `.js` files in this package scope as ES modules, allowing modern `import`/`export` syntax. It does not make TypeScript itself executable; `tsx` is used for that in the dev script.
- **`devDependencies`** — tools needed for development/type-checking.
- **`dependencies`** — packages listed as regular runtime dependencies; currently `tsx` is here.

> Reminder: `package.json` must be valid JSON. Unlike `tsconfig.json` (which TypeScript accepts as JSON with comments/JSONC), `package.json` does **not** support `//` comments.

## 4. `tsconfig.json` Explained

`tsconfig.json` configures TypeScript: which source files to include, how modules are interpreted, what JavaScript target is used, and which type-checking rules are enabled.

### File layout

```json
"rootDir": "./src",
"outDir": "./dist"
```

- **`rootDir`** — the source-code root TypeScript expects to compile.
- **`outDir`** — destination folder for generated output when TypeScript emits files. Source in `src/` is emitted into `dist/`.

### Environment / module settings

```json
"module": "esnext",
"target": "esnext",
"moduleResolution": "bundler",
"types": ["node"]
```

- **`module: "esnext"`** — preserves modern ES module syntax in the compiler output.
- **`target: "esnext"`** — asks TypeScript to target modern JavaScript features rather than down-leveling to an older standard. The exact runtime compatibility depends on the Node version used.
- **`moduleResolution: "bundler"`** — uses a resolution strategy designed for bundler-oriented environments. If this project is intended to run compiled files directly in Node, revisit this setting as part of configuring a Node-specific TypeScript build; bundler resolution and direct Node resolution have different rules.
- **`types: ["node"]`** — includes Node type definitions, so Node globals and APIs can be type-checked.

### Output options

```json
"sourceMap": true,
"declaration": true,
"declarationMap": true
```

- **`sourceMap`** — creates source-map files that help map generated JavaScript back to TypeScript while debugging.
- **`declaration`** — emits `.d.ts` type declaration files describing the generated code's types.
- **`declarationMap`** — emits maps connecting declaration files to the original TypeScript source.

These are more useful when building a library or a compiled project. For a simple learning server run by `tsx watch`, you may not need all three yet.

### Strict type-checking options

```json
"noUncheckedIndexedAccess": true,
"exactOptionalPropertyTypes": true,
"strict": true
```

- **`strict`** — enables a group of stricter type-checking rules, helping catch unsafe or unclear code.
- **`noUncheckedIndexedAccess`** — when accessing an array or index-signature value, TypeScript makes you account for the possibility that the value may be missing (`undefined`).
- **`exactOptionalPropertyTypes`** — treats optional properties more precisely; an optional property is not automatically the same as explicitly assigning `undefined` unless the type allows it.

### Other options

- **`verbatimModuleSyntax: true`** — preserves import/export syntax according to the written code and supports clearer type-only imports/exports.
- **`isolatedModules: true`** — checks that files are compatible with single-file transpilation approaches used by tools such as `tsx`.
- **`noUncheckedSideEffectImports: true`** — checks side-effect-only imports (imports with no imported names) for unresolved modules.
- **`moduleDetection: "force"`** — treats files as modules, even when they do not contain an explicit import/export.
- **`skipLibCheck: true`** — skips type-checking declaration files from dependencies, speeding up checks and avoiding errors inside external type packages.
- **`include: ["src/**/*.ts"]`** — includes TypeScript files under `src`.
- **`exclude: ["node_modules", "dist"]`** — excludes dependency and generated-output folders from the project file search.

### Why are comments allowed in `tsconfig.json` but not `package.json`?

TypeScript reads `tsconfig.json` as a JSON-with-comments format (JSONC), so `//` comments are allowed there. `package.json` is parsed as strict JSON by npm, so comments make it invalid.

## 5. `src/server.ts` — The HTTP Server

Current code:

```ts
import { createServer } from "http";

const server = createServer((req, res) => {
  console.log(req);
})

server.listen(5000, () => {
  console.log("Server is running on the port 5000")
})
```

### Line-by-line

#### `import { createServer } from "http";`

Imports the `createServer` function from Node's built-in `http` module. This module lets us create an HTTP server without Express. `createServer` is imported using named-import syntax.

#### `const server = createServer((req, res) => { ... })`

Creates an HTTP server. The callback runs whenever the server receives a request.

- **`req` (request)** — contains details about the incoming request, such as method, URL, headers, and other request information.
- **`res` (response)** — used to send a response back to the client (browser, API client, etc.).

#### `console.log(req);`

Prints the incoming request object in the terminal. It is useful for inspecting what Node receives, but printing the entire object is usually noisy; later, inspect selected properties such as `req.method` and `req.url` instead.

**Important current behavior:** This code logs the request but never sends a response (`res.end()`, `res.write()`, etc. are not called). A browser/client may keep waiting because the response is not completed. This is intentional/unfinished learning code, not a complete server response.

#### `server.listen(5000, () => { ... })`

Starts the server and makes it listen on port `5000`. The callback runs once the server has started listening.

- **Port 5000** — the local port clients can connect to.
- The server can be visited at `http://localhost:5000` on the same computer.
- **`localhost`** refers to the local machine; `5000` is the port where this server is listening.

#### `console.log("Server is running on the port 5000")`

Prints a message after the server successfully starts listening, so we know it started.

## 6. What Happens When You Run `npm run dev`?

1. npm looks inside `package.json` and finds the script named `dev`.
2. It executes `tsx watch ./src/server.ts`.
3. `tsx` loads and runs `src/server.ts` as TypeScript.
4. `createServer()` creates an HTTP server and registers the request handler.
5. `server.listen(5000)` starts listening for connections on port 5000.
6. The terminal prints `Server is running on the port 5000`.
7. When you visit `http://localhost:5000`, the callback runs, `req` is logged, but the current code does not finish the HTTP response—so the client waits.
8. When you edit the watched source file, `tsx watch` re-runs the development process.

## 7. Recommended Learning / Setup Order

Follow this sequence so each step builds on the previous one:

1. **Create the project** — `npm init -y` (only for a new folder).
2. **Set module mode** — add/understand `"type": "module"` in `package.json` to use ES module syntax.
3. **Install TypeScript** — `npm i -D typescript`.
4. **Install Node type definitions** — `npm i -D @types/node`.
5. **Install the TypeScript runner** — `npm i tsx`.
6. **Create `tsconfig.json`** — configure source folder, output folder, Node types, module settings, and strict checking.
7. **Create `src/server.ts`** — import Node's HTTP module and create a server.
8. **Start the server** — `npm run dev` and verify the startup message.
9. **Handle the response** — add `res.statusCode`, headers, and `res.end()` so the client receives a completed response.
10. **Inspect requests** — log `req.method`, `req.url`, and headers instead of the entire request object.
11. **Learn routing** — handle different paths and HTTP methods manually.
12. **Build a small Raw Node REST API** — implement GET, POST, PATCH, and DELETE before moving to Express.

## 9. Notes / Things to Revisit Later

- The current server is only a starting point: it logs requests but does not send a response yet.
- The `test` script is a placeholder, not a working test setup.
- `main` currently points to `server.ts`; for production compiled output, update it to the actual build entry point later.
- `moduleResolution: "bundler"` is worth revisiting when configuring a TypeScript project that will run emitted JavaScript directly in Node.
- Consider moving `tsx` to `devDependencies` if it is only used for local development.
- Do not put comments in `package.json`; put explanatory notes in this README or other Markdown notes.

## 10. Learning Rule

Whenever a new command or configuration option is introduced, write down:

1. **What is it?**
2. **Why do we need it?**
3. **What happens if we remove it or change it?**
4. **Is it needed during development, build time, or runtime?**

Understanding these four questions will make your Raw Node.js learning much more practical than simply copying setup commands.
